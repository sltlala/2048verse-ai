# 2048verse 4x4 自动刷分 AI

针对 [2048verse.com/4x4](https://2048verse.com/4x4) 的自动化脚本：打开独立 Chrome 窗口，登录账号后由
**Expectimax（期望极大极小）AI** 自动游戏，页面右上角实时可视化每一步决策，并把每局成绩与终局截图存档。

- 纯 Node.js 实现，**无需下载浏览器内核**（复用系统已安装的 Chrome）
- 概率模型按网站**实测**的真实生成率建模（不是照抄默认值）
- 自适应思考预算：开局快、后期深，总耗时低但关键期搜索更深
- 页面跳转/登录/断线都不会导致脚本退出

> ⚠️ 仅供学习与算法研究。自动化游戏可能不符合网站的公平竞争预期，且网站会保存对局回放，
> 请自行判断使用场景与频率。

## 当前策略（AI 策略总览）

### 1. 搜索算法：Expectimax + 迭代加深 + 置换表

- **玩家节点**取 max（4 个方向取最优）
- **随机节点**按真实生成概率取期望
- **迭代加深**：从深度 2 逐层加深；用"实测相邻两层耗时比"预测下一层开销，deadline 兜底中止
- **置换表**：数值哈希开地址表（2²² = 419 万槽），命中即复用；实测比 `Map<string,...>` 快 3-5 倍
- 搜索采用**就地修改 + 回滚**，递归过程零内存分配

### 2. 启发式评估：nneonneo 经典参数

四项加权：**空格数**（+270）、**合并潜力**（+700）、**单调性**（−47）、**数值惩罚**（−11）。

其中合并潜力按 nneonneo 语义统计"隔空格可合并对"——`[2,_,2]` 滑动后确实能合并，应计入。

> **关于"蛇形结构权重"**：已实现并做过 **80 局对照实验**（4 组 × 20 局，固定深度 4），
> 组间差异全部落在统计误差内。结论：**启发式调参无效，默认关闭**（省约 20% 评估开销）。
> 单局分数标准差高达 8-13 万，判断棋力差异需要每组 50 局以上。

### 3. 自适应思考预算：前期快、后期深

实验证明**搜索深度是唯一有效的棋力杠杆**，因此把时间集中投在决胜的后期：

| 空格数 | 预算比例 | 默认 (--budget 150) |
|---|---|---|
| ≥9（开局） | 8% | 12ms |
| 7-8 | 15% | 23ms |
| 5-6（中期） | 25% | 38ms |
| 3-4（后期） | 60% | 90ms |
| ≤2（关键期） | **150%** | **225ms** |

依据：后期局面分支少、搜索便宜——预算 150ms→400ms 时，残局从 11 层加深到 13 层、
关键期从 12 层到 17 层，是性价比最高的投入。

### 4. 概率模型必须与网站一致（关键教训）

用网站 `gameState.fourSpawns` 计数器**实测 6,794 次生成**，得到真实生成 4 概率：

```
生成 4 次数 658 / 6,794 次  →  9.69%
若真值 10%: 标准误 ±0.36%   （吻合）
若真值 20%: 标准误 ±0.49%   （偏差 21 个标准差，不可能）
```

早期版本误按 20% 建模，把搜索资源浪费在高估的风险分支上。修正概率模型后，
最高分从 173,088 提升到 386,636（**2.2 倍**）。可用 `node measure-rate.js` 自行复测。

### 5. 稳定性设计

- 所有页面操作封装为"跳转/关闭时返回 null 而非抛异常"，脚本**不会因页面跳转而退出**
- 登录检测基于 URL + 全站导航链接（登录页自身没有 "Log In" 链接，必须排除，否则误判）
- 页面离开游戏界面时耐心等待，回来后自动恢复并重注入 HUD
- 输入丢失自动重按；标签页被关自动寻找或新建游戏页
- **不向 Chrome 传任何非标准标志** → 不出现"不受支持的命令行标记"警告，同时保留沙箱

## 快速开始

### 方式一：双击一键脚本（推荐）

直接**双击 `start.bat`**，它会自动完成：

1. 检查 Node.js，缺失则用 `winget` 自动安装（无 winget 时给出下载链接）
2. 检查 npm
3. 检查 Google Chrome，缺失则自动安装（脚本用系统 Chrome，无需下载浏览器内核）
4. 安装 Node 依赖（使用项目内 `.npm-cache`，避开系统缓存权限问题）
5. 清理上次残留的自动化 Chrome 窗口（只清理本项目的，不影响你自己的浏览器）
6. 启动游戏

```bat
start.bat                          REM 默认启动
start.bat --speed 0 --budget 200   REM 更快 + 更强
start.bat --env-check              REM 只检查环境, 不启动游戏
start.bat --window max             REM 最大化窗口
```

### 方式二：手动运行

```bash
# 1. 安装依赖 (需要本机已装 Node.js 和 Google Chrome)
npm install

# 2. 运行: 会弹出 Chrome 窗口
node run.js
```

### 首次登录

运行后会弹出独立 Chrome 窗口。点击右上角 **Log In** 登录一次即可，
登录状态保存在 `.chrome-profile/`，以后运行无需再登录。

登录过程页面会跳转，脚本会耐心等待，**不会退出**；登录完成后自动回到游戏页开始挂机。

按 **Ctrl+C** 随时停止。

## 命令行参数

| 参数 | 说明 | 默认 |
|---|---|---|
| `--games N` | 玩 N 局后自动停止 | 无限 |
| `--speed MS` | 每步基础延迟（毫秒），0 = 最快 | 30 |
| `--budget MS` | 思考预算基准值（按空格数自适应缩放） | 150 |
| `--p4 PCT` | 生成 4 的概率（%），**需与网页一致** | 10 |
| `--window MODE` | 窗口尺寸：`none`/`max`/`fullscreen`/`fit`/`1600x900` | `none` |
| `--newgame` | 启动时放弃当前局面，直接开新局 | 接着玩 |
| `--guest` | 不等待登录 | 需登录 |
| `--no-adaptive` | 关闭自适应预算，全程用满（对照实验用） | 自适应 |
| `--profile DIR` | 浏览器数据目录 | `.chrome-profile` |
| `--depth N` / `--snake W` | 固定搜索深度 / 蛇形权重（实验用） | 0 / 0 |

示例：

```bash
node run.js --games 5                    # 玩 5 局
node run.js --speed 0 --budget 200       # 冲分模式
node run.js --window fullscreen          # 全屏，游戏区最大
node run.js --profile .chrome-profile2   # 换配置目录（多开）
```

## 运行结果自动保存

每局结束后自动保存**数据 + 终局截图**（在开新局之前抓取，保证是终局画面）：

```
results/
├── results.jsonl      # 每局一行 JSON (便于分析)
├── history.json       # 同一批数据的数组形式
└── screenshots/
    └── 386636_2026-09-25_19-43-07.png   # 命名: <分数>_<时间点>.png
```

| 字段 | 说明 |
|---|---|
| `endTime` / `endTimeLocal` | 结束时间（ISO / 本地时间戳） |
| `score` | 总分数 |
| `tileSum` | 终局棋盘所有方块数值之和 |
| `moves` | 步数 |
| `fourSpawns` / `fourSpawnPct` | 生成 4 的次数 / 百分比 |
| `maxTile` | 最大方块 |
| `durationMin` | 本局用时（分钟） |
| `gameId` | 网站的局 ID |
| `board` | 终局 4×4 棋盘 |
| `screenshot` | 截图相对路径 |
| `label` | `gameover` 正常结束 / `interrupted` 手动中断 |
| `config` | 本局所用引擎参数 |

离线模拟（`sim.js`）也会把每局结果写入 `results/sim-results.jsonl`。

## 实验记录

### 生成 4 的真实概率（实测）

| 统计量 | 数值 |
|---|---|
| 总生成次数 | 6,794 |
| 生成 4 次数 | 658 |
| **实测概率** | **9.69%** |

### 引擎 A/B：蛇形结构权重（80 局）

| 蛇形权重 | 平均分 | 中位数 | 最高 | 均值标准误 |
|---|---|---|---|---|
| 0（关闭） | 114,642 | 128,988 | 226,016 | ±12,000 |
| 0.15 | 113,333 | 80,564 | 267,424 | ±13,000 |
| 0.3 | 120,011 | 133,228 | 176,620 | ±9,000 |
| 0.6 | 121,368 | 131,268 | 177,468 | ±12,000 |

结论：**差异在误差内，蛇形项无显著效果**，默认关闭。

### 合并潜力计数方式对照

只统计"紧邻相等对"（`--strict-merges`）3 局均值 28.4 万 vs 隔空格计数 24.2 万，
同样在噪声范围内；但隔空格计数更符合游戏规则语义（滑动后确实能合并），故保留。

### 搜索吞吐量优化

| 优化项 | 做法 | 效果 |
|---|---|---|
| 迭代加深停止规则 | 用实测两层耗时比预测下一层；余量足时继续加深 | 不再浪费一半预算 |
| 置换表扩容 | 2²⁰ → 2²²（419 万槽） | 哈希冲突减少，深搜命中率提升 |
| 深度上限 | 14 → 20 层 | 关键期解封（12 → 17 层） |
| 预算曲线重构 | 中期压到 25%，关键期 1.5 倍 | 后期/残局深度显著提升 |

代表性局面深度（预算 150ms）：

| 局面 | 优化前 | 优化后 |
|---|---|---|
| 开局(12空) | 8 | **12** |
| 中盘(6空) | 5 | 5 |
| 后期(3空) | 9 | **10** |
| 关键(1空) | 12 | **17** |
| **平均** | **8.29** | **9.71** |

### 循环级开销压缩（耗时分解实测）

| 环节 | 优化前 | 优化后 | 做法 |
|---|---|---|---|
| 读状态 | 5-8ms | **2.8ms** | 与 HUD 刷新合并为一次页面往返 |
| 无效重算 | 常见 | **0.0ms** | 先校验上一步生效再思考 |
| 按键 | 4.4ms | 4.4ms | — |

现在耗时的 95% 都用于 AI 思考，通信开销已压到最低。

## 工作原理

1. 通过 Playwright 启动**持久化** Chrome 窗口（登录状态保存在项目内配置目录）
2. 每步从 `localStorage.gameState4x4` 读取权威棋盘状态（比解析 DOM 更可靠）
3. AI 用 Expectimax 迭代加深搜索计算最佳方向
4. 混用方向键 / WASD 输入，带可控延迟与抖动
5. 自动设置 `winScreenDisabled=true`，合成 2048 时不弹窗，继续冲更高分
6. 游戏结束自动点击"新游戏"开下一局，循环刷分；成绩与截图自动存档
