# 2048verse 4x4 自动刷分 AI

针对 [2048verse.com/4x4](https://2048verse.com/4x4) 的自动化脚本：打开独立 Chrome 窗口，登录账号后由
**Expectimax（期望极大极小）AI** 自动游戏，页面右上角实时可视化每一步决策，并把每局成绩与终局截图存档。

- 纯 Node.js 实现，**无需下载浏览器内核**（复用系统已安装的 Chrome）
- 概率模型按网站**实测**的真实生成率建模（不是照抄默认值）
- 自适应思考预算：开局快、后期深，总耗时低但关键期搜索更深
- 页面跳转/登录/断线都不会导致脚本退出

> ⚠️ 仅供学习与算法研究。自动化游戏可能不符合网站的公平竞争预期，且网站会保存对局回放，
> 请自行判断使用场景与频率。

## 当前策略（AI 策略总览）

### 1. 搜索算法：Expectimax + 迭代加深 + 置换表

- **玩家节点**取 max（4 个方向取最优）
- **随机节点**按真实生成概率取期望
- **迭代加深**：从深度 2 逐层加深；用"实测相邻两层耗时比"预测下一层开销，deadline 兜底中止
- **置换表**：数值哈希开地址表（2²² = 419 万槽），命中即复用；实测比 `Map<string,...>` 快 3-5 倍
- 搜索采用**就地修改 + 回滚**，递归过程零内存分配

### 2. 启发式评估：nneonneo 经典参数

四项加权：**空格数**（+270）、**合并潜力**（+700）、**单调性**（−47）、**数值惩罚**（−11）。

其中合并潜力按 nneonneo 语义统计"隔空格可合并对"——`[2,_,2]` 滑动后确实能合并，应计入。

> **关于"蛇形结构权重"**：曾做过 **80 局对照实验**（4 组 × 20 局，固定深度 4），组间差异全部落在统计误差内。
> 但这批对局都在 8192 之前就结束了，**从未进入 16384/32768 的后期崩盘区间**——所以该结论只适用于中前期。
> 现在改为**仅在后期（空格 ≤4）启用**，中前期仍关闭（不影响速度）。详见第 6 节。

### 3. 自适应思考预算：前期快、后期深

实验证明**搜索深度是唯一有效的棋力杠杆**，因此把时间集中投在决胜的后期：

| 空格数 | 预算比例 | 默认 (--budget 150) |
|---|---|---|
| ≥9（开局） | 8% | 12ms |
| 7-8 | 15% | 23ms |
| 5-6（中期） | 25% | 38ms |
| 3-4（后期） | 60% | 90ms |
| ≤2（关键期） | **150%** | **225ms** |

依据：后期局面分支少、搜索便宜——预算 150ms→400ms 时，残局从 11 层加深到 13 层、
关键期从 12 层到 17 层，是性价比最高的投入。

### 4. 概率模型必须与网站一致（关键教训）

用网站 `gameState.fourSpawns` 计数器**实测 6,794 次生成**，得到真实生成 4 概率：

```
生成 4 次数 658 / 6,794 次  →  9.69%
若真值 10%: 标准误 ±0.36%   （吻合）
若真值 20%: 标准误 ±0.49%   （偏差 21 个标准差，不可能）
```

早期版本误按 20% 建模，把搜索资源浪费在高估的风险分支上。修正概率模型后，
最高分从 173,088 提升到 386,636（**2.2 倍**）。可用 `node measure-rate.js` 自行复测。

### 5. 后期（关键期）专项优化 — 已实现，但**默认关闭**

**失败复盘**：实测一局跑到 669,900 分 / 32768 方块后死亡，终局盘面为：

```
     2     4   512     8
    16    32    16     2
   256   128    64     8
 32768 16384    16     2
```

程序逐方向验证：**↑↓←→ 全部不可行**（满盘 16/16 且无任何相邻相等对）。
缺少 1024/2048/4096/8192 四块——它们已被吃进 16384/32768，而新的阶梯没能重建起来。
终局 Tile Sum 仅 50,218，而 32768 满阶梯需要 65,534。

定位到三个算法弱点并分别修正：

| 弱点 | 原实现的问题 | 优化 |
|---|---|---|
| **死局信号被稀释** | 死局只罚 −800,000，而随机节点要对 14 个分支**取平均** → 单个死分支只拉低均值约 5.7 万，与普通招式分差同量级，AI 敢赌 | 死局惩罚提到 **−10⁹**，任何通向死局的分支被决定性排除 |
| **关键期用期望值** | "20% 概率被一子打死"会被平均稀释 | 空格 ≤2 时引入**风险厌恶**：`值 = 0.5×期望 + 0.5×最坏` |
| **只约束局部单调性** | nneonneo 单调性只看单行/单列，整体阶梯仍可碎裂 | 空格 ≤4 时启用**蛇形结构项**（8 朝向取最优） |

三项均可在 `ai.js` 的 `configure()` 中调节，便于 A/B：

```js
ai.configure({ deathPenalty: 1e9, riskAversion: 0.5, riskMaxEmpty: 2,
               endgameSnakeW: 0.35, endgameSnakeMaxEmpty: 4 });
```

#### 实测结论：不显著，故默认关闭

**40 局对照实验**（两组各 20 局，固定深度 4；`node ab-endgame.js 20 4`）：

| 变体 | 平均分 | 均值标准误 | 中位数 | 最低分 | 最大方块分布 |
|---|---|---|---|---|---|
| **OFF**（旧行为，默认） | 112,658 | ±10,864 | 134,136 | 27,164 | 2048×2, 4096×6, 8192×12 |
| **ON**（三项优化） | 118,786 | ±9,574 | 132,240 | 56,712 | 4096×9, 8192×11 |

均值差 6,128，**远小于标准误**，中位数几乎相同 → 无统计显著差异。
ON 的最差局更好（最低 56,712 vs 27,164，且没有 2048 崩盘局），但这不足以支撑改动默认值。

**而且大死局惩罚存在"值饱和"风险**：关键期常有多个招式都含致死分支，取平均后
它们全部趋近同一个巨大负值（例如都 ≈ −3.3e8），**招式间的差异被抹平 → 关键期等于随机选**。
nneonneo 原版只用 200,000 的适度惩罚，正是为了避免这个问题。

因此**默认沿用旧行为**（该配置实测跑到 669,900 / 32768）。想实验可显式开启：

```bash
node run.js --endgame on            # 开启三项后期优化
node sim.js 20 30 10 --endgame=on   # 对照测试
```

> 经验教训：单局分数标准差高达 5-13 万，**2 局的结果不足以判断回归**。
> 上表里 8192 是两种配置下最常见的结局，所以"某几局只到 8192"属正常波动。

### 6. 稳定性设计

- 所有页面操作封装为"跳转/关闭时返回 null 而非抛异常"，脚本**不会因页面跳转而退出**
- 登录检测基于 URL + 全站导航链接（登录页自身没有 "Log In" 链接，必须排除，否则误判）
- 页面离开游戏界面时耐心等待，回来后自动恢复并重注入 HUD
- 输入丢失自动重按；标签页被关自动寻找或新建游戏页
- **不向 Chrome 传任何非标准标志** → 不出现"不受支持的命令行标记"警告，同时保留沙箱

## 快速开始

### 启动脚本一览

启动脚本按**有头 / 无头**分成独立文件，另有一个总菜单：

| 脚本 | 用途 |
|---|---|
| **`start.bat`** | 总菜单，双击后选 `1` 有头 / `2` 无头 / `3` 停止 |
| **`start-headed.bat`** | **有头模式**：显示浏览器窗口 + 页面内 HUD，前台运行，`Ctrl+C` 停止 |
| **`start-headless.bat`** | **无头模式**：隐藏窗口后台运行，可用状态面板随时查看 |
| **`stop.bat`** | 停止正在运行的 bot（并释放配置目录锁） |
| `_env-setup.bat` | 公共环境检查（被上面两个启动脚本调用，通常不用直接运行） |
| `start.sh` / `start-headless.sh` / `stop.sh` | Linux / macOS 对应版本 |

两个启动脚本都会先自动完成环境准备：

1. 检查 Node.js，缺失则用 `winget` 自动安装到 **`D:\Program_software\nodejs`**（无 winget 时给出下载链接）
2. 检查 npm
3. 检查 Google Chrome（脚本用系统 Chrome，无需下载浏览器内核）
4. 安装 Node 依赖（使用项目内 `.npm-cache`，避开系统缓存权限问题）

> **工具安装目录**：统一装到 `D:\Program_software\<工具名>`（会自动创建），并优先复用该目录下已有的 Node.js。
> 唯一例外是 Google Chrome —— 官方安装程序不支持自定义路径。该目录可通过 `_env-setup.bat` 顶部的 `TOOLS_DIR` 修改。
>
> **关于脚本语言**：`.bat` 文件刻意使用英文提示。因为 cmd.exe 解析含多字节字符（中文）的批处理文件时会
> 出现偏移错乱，把后续行拆成乱码命令（实测过 UTF-8 与 GBK 两种编码都不稳定）。游戏日志的中文输出不受影响。

### 有头模式（推荐先用它登录）

```bat
start-headed.bat                      REM 显示浏览器窗口 + HUD
start-headed.bat --speed 0 --budget 200   REM 透传参数给 run.js
```

窗口可见、页面右上角有实时 HUD、本窗口 `Ctrl+C` 即停止。**首次登录必须用有头模式**（无头没窗口可输入）。

### 无头模式（后台挂机）

```bat
start-headless.bat                    REM 隐藏窗口后台运行
```

启动后固定开启两个查看通道：

- **状态面板**：浏览器打开 **http://127.0.0.1:8765** —— 每 3 秒自动刷新，含实时截图、得分、决策方向、深度、速度、4×4 小棋盘
- **定时截图**：每 10 秒写入 `results/screenshots/live.png`，随时可打开
- **日志**：`logs/bot.log`
- **停止**：双击 `stop.bat`

无头启动器内置保护：检测到已有实例在运行会拒绝启动（避免配置目录冲突）；启动时会清理残留的自动化 Chrome 窗口。

停止方式见 [`stop.bat`](#停止正在运行的-bot) 或手动命令（见下文"停止 bot"）。

### 停止正在运行的 bot

无头模式没有控制台可 `Ctrl+C`，用以下任一方式：

```bat
stop.bat                          REM 最简单: 双击即可
```

```powershell
# 手动: 停 bot 进程
Get-CimInstance Win32_Process | Where-Object { $_.Name -eq 'node.exe' -and $_.CommandLine -match 'run\.js' -and $_.CommandLine -notmatch 'dsh' } | ForEach-Object { Stop-Process -Id $_.ProcessId -Force }
# 再清理浏览器 (必须, 否则配置目录被占, 下次启动会失败)
Get-CimInstance Win32_Process | Where-Object { $_.Name -eq 'chrome.exe' -and $_.CommandLine -like '*2048\.chrome-profile*' } | ForEach-Object { Stop-Process -Id $_.ProcessId -Force }
```

```powershell
# 通用: 通过端口反查 PID
Get-NetTCPConnection -LocalPort 8765 | Select-Object -ExpandProperty OwningProcess
```

## 命令行参数

| 参数 | 说明 | 默认 |
|---|---|---|
| `--games N` | 玩 N 局后自动停止 | 无限 |

## 实验记录

### 生成 4 的真实概率（实测）

| 统计量 | 数值 |
|---|---|
| 总生成次数 | 6,794 |
| 生成 4 次数 | 658 |
| **实测概率** | **9.69%** |

### 引擎 A/B：蛇形结构权重（80 局）

| 蛇形权重 | 平均分 | 中位数 | 最高 | 均值标准误 |
|---|---|---|---|---|
| 0（关闭） | 114,642 | 128,988 | 226,016 | ±12,000 |
| 0.15 | 113,333 | 80,564 | 267,424 | ±13,000 |
| 0.3 | 120,011 | 133,228 | 176,620 | ±9,000 |
| 0.6 | 121,368 | 131,268 | 177,468 | ±12,000 |

结论：**差异在误差内，蛇形项无显著效果**，默认关闭。

### 合并潜力计数方式对照

只统计"紧邻相等对"（`--strict-merges`）3 局均值 28.4 万 vs 隔空格计数 24.2 万，
同样在噪声范围内；但隔空格计数更符合游戏规则语义（滑动后确实能合并），故保留。

### 搜索吞吐量优化

| 优化项 | 做法 | 效果 |
|---|---|---|
| 迭代加深停止规则 | 用实测两层耗时比预测下一层；余量足时继续加深 | 不再浪费一半预算 |
| 置换表扩容 | 2²⁰ → 2²²（419 万槽） | 哈希冲突减少，深搜命中率提升 |
| 深度上限 | 14 → 20 层 | 关键期解封（12 → 17 层） |
| 预算曲线重构 | 中期压到 25%，关键期 1.5 倍 | 后期/残局深度显著提升 |

代表性局面深度（预算 150ms）：

| 局面 | 优化前 | 优化后 |
|---|---|---|
| 开局(12空) | 8 | **12** |
| 中盘(6空) | 5 | 5 |
| 后期(3空) | 9 | **10** |
| 关键(1空) | 12 | **17** |
| **平均** | **8.29** | **9.71** |

### 循环级开销压缩（耗时分解实测）

| 环节 | 优化前 | 优化后 | 做法 |
|---|---|---|---|
| 读状态 | 5-8ms | **2.8ms** | 与 HUD 刷新合并为一次页面往返 |
| 无效重算 | 常见 | **0.0ms** | 先校验上一步生效再思考 |
| 按键 | 4.4ms | 4.4ms | — |

现在耗时的 95% 都用于 AI 思考，通信开销已压到最低。

## 工作原理

1. 通过 Playwright 启动**持久化** Chrome 窗口（登录状态保存在项目内配置目录）
2. 每步从 `localStorage.gameState4x4` 读取权威棋盘状态（比解析 DOM 更可靠）
3. AI 用 Expectimax 迭代加深搜索计算最佳方向
4. 混用方向键 / WASD 输入，带可控延迟与抖动
5. 自动设置 `winScreenDisabled=true`，合成 2048 时不弹窗，继续冲更高分
6. 游戏结束自动点击"新游戏"开下一局，循环刷分；成绩与截图自动存档

## 成绩上传保证与排名刷新

网站的成绩上传机制（源码分析所得）**很脆弱**：

```js
// 死局那一刻才触发, 且未登录不上传、失败只弹 alert、没有重试
if (死局 && variant !== "Replay") { J("gameOver"); L && ke(board, score, ...); }
ke = async (...) => {
  if (!有用户名) return;
  fetch(`${backend}/games/upload`, { method:"POST", credentials:"include", body: gzip(payload) })
    .then(res => { if (!res.ok) alert("There was an error logging your game!..."); });
}
```

实测教训：一局 **669,900（32768）** 的分数**从未上传成功**——因为脚本在局末立刻点"新游戏"，
异步上传请求被打断，服务器最高分至今仍是后续对局的 177,308。

为此脚本现在每局执行**三步保护**：

| 步骤 | 动作 |
|---|---|
| ① 抓取 | 局末**先**截图并存下终局数据（刷新前完成） |
| ② 校验 | 轮询排行榜接口的 **`hs` 字段**（服务器侧本人最高分），直到 `hs >= 本局分数` 才算成功 |
| ③ 刷新 | 确认后刷新页面，让排行榜与"最高分"显示最新数据，再开下一局 |

输出示例：

```
  等待网站成绩上传 (账号 sltlala, 本局 289,800)...
  ✅ 上传成功: 服务器最高分 289,800, 当前排名 #344 (等待 4s)
  🔄 页面已刷新: 服务器最高分 289,800 | 排名 #344 | 页面显示最高分 289,800
```

失败时明确告警（不会静默）：

```
  ❌ 上传未确认!
     服务器最高分: 177,308 | 本局 669,900
     网站已弹出"记录上传失败"提示 → 该对局未被服务器接收
     截图与数据已存档, 可凭截图到官方 Discord 申请手动补录
```

记录里新增 `upload`（`ok`/`failed`/`guest`）、`serverBestAfter`、`rankAfter` 字段，可事后审计。

相关参数：`--upload-timeout SEC`（等待确认上限，默认 60）、`--restart-delay SEC`（额外间隔，默认 5）。

> 补充：网站的 `hs` 字段既可用于校验上传，也可用来直接查询自己当前的服务器最高分与排名：
> ```
> https://backend.2048verse.com/leaderboard/top?time=all&username=<你的用户名>&variant=4x4
> ```

## 部署到服务器

完全支持。服务器上没有显示器，用**无头模式**运行，截图与数据照常保存。

### 方式一：Docker（推荐）

镜像自带 Chromium 和中文字体，不依赖宿主机环境：

```bash
# 1. 本地导出登录会话 (见下方"登录态处理")
node run.js --export-session session.json

# 2. 把项目 + session.json 传到服务器, 然后:
docker compose up -d --build

# 3. 查看日志 / 数据
docker compose logs -f
ls results/screenshots/
```

`docker-compose.yml` 已挂载两个持久化目录：`.chrome-profile`（登录态）与 `results`（数据+截图），
容器重启不会丢数据；`restart: unless-stopped` 保证崩溃后自动拉起。

### 方式二：直接跑（Linux）

```bash
./start.sh --headless --newgame --browser chromium
# 或
npx playwright install --with-deps chromium   # 首次需装浏览器
node run.js --headless --newgame --browser chromium
```

### 方式三：systemd 常驻

```ini
# /etc/systemd/system/2048verse.service
[Unit]
Description=2048verse AI bot
After=network.target

[Service]
WorkingDirectory=/opt/2048verse-ai
ExecStart=/usr/bin/node run.js --headless --newgame --browser chromium
Restart=always
RestartSec=10
User=botuser

[Install]
WantedBy=multi-user.target
```

### 登录态处理（关键）

**不能直接把 Windows 上的 `.chrome-profile` 拷到 Linux** —— Chrome 的 Cookie 在 Windows 上由
DPAPI 加密，换个系统就解不开。正确做法是用 Playwright 的 `storageState` 导出明文会话：

```bash
# 本地(已登录的机器)上执行: 导出会话, 然后脚本自动退出
node run.js --export-session session.json

# 服务器上: 导入会话, 免去在服务器上登录
node run.js --headless --session session.json --browser chromium
```

> `session.json` 含登录凭证，请勿提交到仓库（已在 `.gitignore` / `.dockerignore` 中排除），
> 并注意设置文件权限 `chmod 600 session.json`。

### 数据与截图

服务器上的输出与本地完全一致：

```
results/
├── results.jsonl                      # 每局一行 JSON
├── history.json                       # 数组形式
└── screenshots/<分数>_<时间点>.png     # 终局截图 (无头模式下同样正常渲染)
```

可选：每局结束后把结果 POST 到你的接口（做通知/入库）：

```bash
node run.js --headless --webhook https://your-server/api/2048-result
```

### 服务器注意事项

| 事项 | 说明 |
|---|---|
| 资源占用 | 单个 Chromium 实例约 300-600MB 内存；1 核 1G 的小机器够用 |
